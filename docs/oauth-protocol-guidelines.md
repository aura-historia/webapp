# OAuth Protocol Guidelines

Apply this guide to changes under `src/features/oauth` and `src/features/oauth-client-broker`.

## Invariants

- Preserve PKCE verifier behavior, `state`, redirect URI handling, and requested scopes.
- Do not weaken, omit, reinterpret, or silently replace these controls during a refactor.
- Treat authorization codes, state, verifiers, tokens, client secrets, and redirect data as sensitive: never place them in logs, analytics, public caches, or unnecessary UI.

## Change Review

- Verify authorization requests and callbacks preserve the existing protocol semantics.
- Make scope and consent screens accurately reflect requested permissions.
- Require explicit security/product review before changing a protocol invariant.

## Browser entry, resource and login return

- The browser entry is the existing `/$lng/oauth/authorize` route, named by the backend's RFC 8414 metadata: `https://aura-historia.com/en/oauth/authorize` in production and `https://stage.aura-historia.com/en/oauth/authorize` on stage. English is the discoverable default; the locale switch keeps the whole query, so a language change preserves every OAuth parameter.
- The optional RFC 8707 `resource` (for MCP clients `https://mcp.aura-historia.com/v1`, on stage `https://mcp.stage.aura-historia.com/v1`) travels like `scope` and `state`: the route schema, the approval form, the server-side form parser, backend forwarding and login return carry it unchanged, and a change discards request-bound source selection. The webapp never adds, defaults or rewrites it; the backend validates and binds it to the code.
- The router JSON-parses search values, so the route schema turns numbers, booleans and `null` back into their original text (a `state` of `123` is echoed as `123`). A value that is itself other JSON, such as `"x"` or `1.0`, is still normalized by the router; clients send opaque random state, so this is not supported input.
- Signed-out visitors reach `/$lng/login?redirect=<consent path and query>` from the `_auth` guard, and an unauthenticated approval post rebuilds the same path from its form fields. Password sign-in and an existing session continue to that path. Federated sign-in carries it in the Cognito custom state, limited to a 2,048-character path and a 4,096-character state. A request with every canonical scope, the MCP resource and a 43-character MCP state needs about 800 characters, leaving room for client states of about 1,000 characters; a WooCommerce broker consent path, the broker's browser entry with the plugin's four scopes and the merged reference, needs about 390 characters. A longer destination is never dropped silently: the provider buttons show a localized message instead of starting the redirect, and email sign-in has no such limit.
- MCP clients use direct registered callbacks and do not set `requires_listing_source_id`, so no granted sources are read or selected and no `listing_source_id` is added. Only the WooCommerce broker exchanges a code server-side, through its own transaction flow (below).

## Approval and denial

- `/api/oauth/authorize/approve` accepts only same-origin form posts: `Sec-Fetch-Site: same-origin`, or, from browsers without fetch metadata, an `Origin` equal to the request origin. A cross-site, sibling-subdomain, opaque or origin-less post receives `403` before the session is read or a code is requested. Approval still requires the Cognito session cookie, and the backend redirect with code and state is returned with its `no-store` headers.
- The consent page shows the invalid-request state, with neither approval nor denial, unless the consent metadata belongs to the requested client and lists the redirect URI exactly (RFC 6749 §4.1.2.1). Denial navigates only to that registered URI, keeping any query it was registered with, and adds `error=access_denied` and the original `state`; no code is requested.

## Ordinary-user consent metadata

Backend issue [#1926](https://github.com/aura-historia/backend/issues/1926) supplies `GET /v1/oauth/clients/{clientId}` for signed-in ordinary users authenticated with a Cognito access JWT. Its secret-free response contains client identity, public URLs, registered redirects and allowed scopes. The consent hook reads this endpoint with the shared API client's ordinary-user authentication and maps the response to the internal OAuth model before UI use.

The generated `getOAuthConsentClient` operation supplies `OAuthClientConsentMetadataData`. The feature adapter checks the requested client identity and maps only the public fields to the internal model before UI use. Reads use `cache: no-store`; metadata queries are short-lived and cleared on sign-out/account changes. Unavailable metadata shows the localized unavailable state. Backend authorization remains authoritative for registration, redirects and permissions. Regenerate the client with `pnpm openapi-ts` when the backend contract changes.

## Scopes and listing-source routing

- Consent displays requested scopes with the shared access-token scope definitions and localized descriptions for all canonical backend scopes. Unknown scopes render as the raw identifier without a fabricated description. Requested scopes are shown exactly as requested: read and write siblings are independent and never added, no registered scopes are silently added, and legacy scope names are not translated into new privileges. Administrative scopes do not grant administrator access; the backend applies role, ownership and source checks.
- `getMyListingSources` replaces partner-shop listing. Consent shares the partner views' paged read (`useOwnListingSources`): it shows the first page and requests later pages only when the user asks for more, saying the list is incomplete until the last page. Reads use `cache: no-store` so the browser cannot reuse stale grants. Responses are mapped to internal source references before selection UI. A single source is preselected only when it is the whole list (no further page), and a failed read shows the error state instead of earlier pages. Single-source selection is preserved when explicitly requested. Manual choices are discarded whenever any normalized authorization request field changes (client ID, redirect URI, state, source-selection flag, PKCE challenge, scopes, response type, challenge method or resource), including when navigating back to an earlier request. Requests with source selection disabled never submit a cached source ID.
- `requires_listing_source_id` replaces the partner-shop selection flag. The selected canonical `listingSourceId` is carried as `listing_source_id` on return links, without adding a backend OAuth authorize parameter.
- The approval form submits `requires_listing_source_id=true` with the selected source, and the approval handler never forwards the flag to the backend. A post with the flag but no `listing_source_id` receives `400` before the session is read, so such a request never yields a code. When the session has expired, the login retry keeps the flag but not the chosen source: after sign-in, consent asks for a source again from the signed-in account's grants.
- Source selection is integration routing information, not source-scoped token authorization. Token permissions follow requested scopes and current backend grants.
- Both single-source confirmation and multiple-source selection explain this permission distinction using integration-neutral copy. Selection is requested only by the explicit flag; a redirect pathname alone does not identify the WooCommerce broker.

## WooCommerce broker protocol v2

This section is the normative contract between the webapp broker (this repository, [#1025](https://github.com/aura-historia/webapp/issues/1025)) and the WooCommerce extension ([woocommerce-extension#126](https://github.com/aura-historia/woocommerce-extension/issues/126)). Both implement it together; [`docs/fixtures/woocommerce-oauth-broker-v2.json`](fixtures/woocommerce-oauth-broker-v2.json) holds the shared request and response fixtures. The wire format (endpoint paths, JSON bodies, the authorization URL shape, the `approved` outcome and the error identifiers) is the one the extension ships from 0.3.2 ([#1195](https://github.com/aura-historia/webapp/issues/1195)); changing any of it breaks installed plugins and needs a coordinated plugin release. The earlier unversioned handshake (base64url JSON state carrying the return URI and PKCE verifier, a forwarded `third_party_exchange_code` and a browser `listing_source_id`) is removed with no compatibility window. A request in the old shape is rejected; its callback ends on an Aura Historia page asking the merchant to restart the connection from WordPress and update the plugin. A direct consent request whose `redirect_uri` is the broker callback, other than the broker's own browser entry (step 1), shows the same message, and the generic approval endpoint refuses it with `400`. No backend change is involved: the broker uses the existing authorize, token, revoke, consent-metadata and source-grant APIs.

### Trust boundaries and values

| Value | Created by | Travels | Purpose |
| --- | --- | --- | --- |
| `client_state` | Plugin, ≥ 32 random bytes | Initiation, merchant handoff, completion response | The plugin's CSRF and callback correlation. Stored, never shown in the browser before the handoff. |
| `completion_secret` | Plugin, ≥ 32 random bytes | Only the WordPress server → broker completion | Per-flow proof. The broker stores its S256 commitment, never the secret. |
| `completion_challenge` | Plugin: `BASE64URL_NO_PADDING(SHA256(ASCII(completion_secret)))` | Initiation | Commitment to the secret; method `S256` only. It is not the OAuth PKCE challenge. |
| `transaction_id` | Broker, 32 random bytes | Initiation response, browser URL, handoff, completion | Opaque correlation handle. Knowing it retrieves nothing. |
| PKCE verifier | Broker, 32 random bytes | Never leaves the server | The ordinary OAuth PKCE verifier; scrubbed from storage once the exchange is claimed. |
| OAuth callback `state` | Broker: `<transaction_id>.<32 random bytes>` | Backend redirect, browser, broker callback | Binds the callback to the approval; stored as a SHA-256 hash. |
| Session binding | Broker, 32 random bytes | `__Secure-ah-wc-<transaction_id>` cookie | Binds the callback to the approving browser; stored as a hash. |
| `completion_code` | Broker, 32 random bytes | Only the merchant handoff and the completion request | Proves receipt of the merchant callback; stored as a hash. Not the backend's `third_party_exchange_code`, which the broker drops and never forwards. |

All random values come from the platform CSPRNG and are base64url without padding: broker values are exactly 43 characters (`^[A-Za-z0-9_-]{43}$`), plugin values 43 to 128 (`^[A-Za-z0-9_-]{43,128}$`). The configured OAuth client (`OAUTH_CLIENT_REDIRECT_BROKER_WOOCOMMERCE_CLIENT_ID`, its secret a Worker secret) and the callback `https://<deployment origin>/api/oauth/client/redirect-broker/woocommerce` are the trust anchors. The deployment origin is the build-time `VITE_APP_URL` (`https://aura-historia.com`, `https://stage.aura-historia.com`); request hosts and forwarded values are never used for it.

### Sequence

1. **Initiate** (WordPress server → broker): `POST /api/oauth/client/redirect-broker/woocommerce/transactions` with a JSON object body (`Content-Type: application/json`, a charset parameter allowed) and a `Content-Length` of at most 8 KiB; the plugin sends `Accept: application/json`. Members, each at most once and no others: `protocol_version` (the JSON number `2`), and as strings `client_id` (the configured canonical `oc_` ID), `merchant_redirect_uri`, `client_state`, `scope`, optional `resource`, `completion_challenge`, `completion_challenge_method` (`S256`). `scope` is one or more canonical scopes separated by single spaces, each once; `resource` an absolute HTTPS URI. Both are kept exactly and validated again by the backend. The broker generates `transaction_id` and its PKCE verifier and stores the transaction. `201` JSON: `protocol_version`, `transaction_id`, `authorization_url` and `expires_at` (RFC 3339 UTC). No code, verifier or readable transaction payload is issued or disclosed. Initiation does not authorize the destination.
   - **Browser entry.** The plugin follows only an OAuth-shaped URL on the broker origin's `/oauth/authorize` route that names its client, `response_type=code` and its exact scope, with an opaque `state` and no other parameters than OAuth's. The `authorization_url` is therefore `https://<origin>/oauth/authorize?client_id=…&redirect_uri=<broker callback>&response_type=code&scope=…&state=<transaction_id>`, which redirects to the visitor's language. The consent route treats exactly this shape (these five parameters, this deployment's callback, `response_type=code` and a `state` shaped like a transaction reference, plus the `transaction_id` the router merges into the location for the sign-in return, which must equal `state`) as the transaction `state` names, and reads client, scope and every other value from the stored transaction, never from the URL. Knowing the URL grants nothing beyond the reference; any other request for the broker callback stays a direct OAuth request and is refused as above.
2. **Consent** (browser ↔ webapp): the consent page reads `GET /api/oauth/broker/woocommerce/consent?transaction_id=…` with the user's session. It returns only `status`, `transaction_id`, `client_id`, `merchant_redirect_uri`, `recipient` (its WordPress site address), `scope`, `resource` and `expires_at` while pending, or `declined`, `answered` or `invalid`. Reading never approves or binds a transaction. The page shows the client's consent metadata, the recipient (host and exact return address), the requested scopes and the user's granted sources; sign-in and the language switch keep the transaction reference. Approval and denial post only `lng`, `transaction_id` and `listing_source_id` as same-origin forms to `/api/oauth/broker/woocommerce/approve` and `/deny`, and the page sends a decision only once; client, recipient, scopes and resource are always read from the stored transaction.
3. **Approve**: same-origin check, Cognito session, then the destination rule below. The broker requests a code from `GET /v1/oauth/authorize` with the user's access JWT, the configured client and callback, the stored scopes, resource and PKCE challenge, and a fresh callback `state`. The backend redirect must name exactly the configured callback, carry the sent `state` and one `code`, and nothing else (`iss` aside); anything else is not forwarded. The broker then atomically freezes the approval (user `sub`, session-binding hash, state hash, source) and redirects the browser to the callback with only `code` and `state`, setting the session-binding cookie (`HttpOnly; Secure; SameSite=Strict`, path of the callback, expiring with the transaction). A backend `invalid_scope` or `invalid_target` refusal (as a `400` or an error redirect) ends the transaction as `failed` with that error, and any other `400` ends it as `failed` with `server_error`; both are handed off to the verified recipient. An unavailable or unexpected backend answer, including any other error redirect, leaves the transaction open (`approval_failed` on the consent page).
4. **OAuth callback** (`GET /api/oauth/client/redirect-broker/woocommerce`): the request must be on the configured callback, with `state` and `code` exactly once and no `error`. The state must have the v2 shape; the binding cookie and the signed-in user must match the approval. A failed attempt changes nothing and leaves the approving browser's cookie in place; the cookie is cleared once the exchange is claimed. The broker atomically claims the exchange (`approved → exchanging`), so duplicate or concurrent callbacks exchange once, and redeems the code at `POST /v1/oauth/token` with the stored verifier, configured client credentials and the stored `resource`. It validates the token response (`access_token`, `token_type` `Bearer`, `scope`, optional non-negative `expires_in`) and stores the credential and the approved source as one result. The plugin has no refresh flow and refuses expiring tokens, so a token issued with `expires_in` is revoked at once and handed off as `failed` with `server_error` instead. It mints a fresh `completion_code`, stores its hash and redirects to the exact `merchant_redirect_uri` with only `transaction_id`, `state` (`client_state`) and `completion_code` appended after its `page` parameter. Verifiers, secrets, tokens, backend codes and source values never appear in the redirect, and other callback parameters are not forwarded. A failed exchange is handed off as `failed` the same way.
5. **Complete** (WordPress server → broker): `POST /api/oauth/client/redirect-broker/woocommerce/transactions/complete`, a JSON object body under the same rules as initiation, members exactly once: `protocol_version` (the number `2`), and as strings `transaction_id`, `completion_code`, `completion_secret`. The endpoint is configured in the plugin, never taken from browser parameters. The broker verifies the code against its hash and the secret against the commitment, then atomically releases the result once. `200` JSON with `outcome`:
   - `approved`: `protocol_version`, `transaction_id`, `client_state`, `listing_source_id`, `access_token`, `token_type` (`Bearer`), `scope`; `resource` only if one was requested (the plugin never requests one, and would refuse a result carrying it). No expiry or refresh token is ever included. Source and credential come from the same approved transaction; a browser-supplied source has no effect.
   - `denied` with `error: access_denied`, or `failed` with `error` one of `invalid_scope`, `invalid_target`, `invalid_grant`, `server_error`, `temporarily_unavailable`: the authoritative terminal outcome, without a credential.

The plugin must not infer success from the browser redirect alone; only the completion response is authoritative.

### Endpoint errors

Initiation and completion errors are JSON `{ "protocol_version": 2, "error": "…", "retryable": … }` with `Cache-Control: no-store`. Only `retryable` errors may repeat the same request; every other error needs a fresh flow. The plugin shows specific guidance for `unsupported_protocol_version`, `invalid_client`, `invalid_scope`, `invalid_destination`, `invalid_completion_code`, `invalid_completion_proof` and the `transaction_*` errors, treats `408`, `429`, `5xx` and `temporarily_unavailable` as unavailable, and shows a generic restart message otherwise.

Both endpoints are exact TanStack Start server routes accepting `POST`. Without an exact route, a request falls through to the app router, whose HTML-only fallback answers JSON requests with `406` and other requests with the HTML not-found page; that is how the mismatch in [#1195](https://github.com/aura-historia/webapp/issues/1195) surfaced. Route tests pin both paths, and a change to either is a contract change.

| Error | Status | Retryable | Meaning |
| --- | --- | --- | --- |
| `invalid_request` | 400 | no | Wrong content type, missing or oversized `Content-Length`, malformed JSON or another top-level value than an object, or a missing, unknown, repeated, nested or mistyped member (`protocol_version` as text, for example). |
| `unsupported_protocol_version` | 400 | no | `protocol_version` is a number other than `2`. Reported before any other problem with the body, so a newer plugin's unknown members do not hide it. |
| `invalid_client` | 400 | no | Not the configured client. |
| `invalid_destination` | 400 | no | The merchant return URI breaks the rules below. |
| `invalid_scope`, `invalid_target` | 400 | no | Unsupported scope or malformed resource. |
| `invalid_completion_challenge` | 400 | no | Missing or malformed commitment, or a method other than `S256`. |
| `invalid_transaction` | 400 | no | Unknown or already removed transaction. |
| `invalid_completion_code`, `invalid_completion_proof` | 400 | no | Wrong completion code, or a secret that does not match the commitment. The transaction is unchanged and the legitimate redeemer can still complete. |
| `transaction_pending` | 409 | yes | Consent or exchange has not finished; nothing can be redeemed yet. |
| `transaction_consumed` | 409 | no | Released before (only reported for the correct code and proof). Treat a lost response as failed and start again. |
| `transaction_expired` | 410 | no | Past the transaction or completion-code lifetime. |
| `rate_limited` | 429 | yes | With `Retry-After: 60`. |
| `server_error` | 500 | no | Broker misconfigured (credentials, client ID or storage binding missing). |
| `temporarily_unavailable` | 503 | yes | Transaction storage unavailable. |

Consent-page outcomes that cannot safely return to the merchant (unknown, expired or tampered transactions, a wrong browser or account, unavailable storage) stay on an Aura Historia page with a localized message (`broker_error`: `invalid_request`, `session_mismatch`, `unavailable`; inline on the open consent: `recipient_not_registered`, `source_unavailable`, `approval_failed`).

### Merchant destination policy

- **Registration.** The backend has no verified merchant origin and the source-grant DTO carries none. The association this protocol relies on is the listing source's website (`url` of `GET /v1/listing-sources/by-slug/{slug}`), which only Aura Historia administrators set, directly or by approving a partnership application. Registering it is the act that authorizes the source's destination; it is not inferred from source names or slugs, client-supplied URLs, certificates, server-to-server requests or stored data.
- **Rule.** At approval, and at denial when a source is chosen, the broker rechecks that the selected `ls_` source is among the user's current grants (`getMyListingSources`, `cache: no-store`, every page as needed up to 5,000 sources). The registered website must then be the WordPress site the plugin runs at: the same origin (scheme, host and port) and the same install path as the return URI's site address. The site address is the return URI without `wp-admin/admin.php?page=…`; for example `https://shop.example/` or `https://host.example/store/`. A trailing slash is optional and the registered URL's query is ignored. Custom domains, ports and subdirectory installs are supported as registered. `www` and apex, other subdomains, other ports and sibling or nested paths on a shared origin are different sites, so one shop on a shared host cannot receive another's connection. A source without a registered website, or with another site address, is refused as `recipient_not_registered`, and the transaction stays open for another choice. The consent page shows this site address as the recipient bound to the approval, the same value the handoff uses.
- **Return URI.** Exactly the plugin's settings page as WordPress builds it, `{site address}wp-admin/admin.php?page=aura-historia-partner-connect` (the extension's `admin_url("admin.php?page=" . PAGE_SLUG)`), with no other query parameter. It must be absolute and already canonical: it equals its own WHATWG serialization, which rejects case, default-port, dot-segment and encoding variants. It is at most 2,048 characters, HTTPS, and has no credentials, fragment, whitespace, control characters or backslashes. The fixed page means no open redirect or other page on the shop can receive the code, and no reserved or PHP-mangled parameter name can collide with the handoff, which is appended after `page`.
- **Development exception.** Only a broker whose own origin is loopback HTTP (`VITE_APP_URL=http://localhost:…`) accepts loopback HTTP return URIs and registered websites (`localhost`, `127.0.0.1`, `[::1]`). Staging and production never do. Renaming the plugin page is a contract change for both repositories.
- **Denial.** A denial is recorded server-side without requesting a code. It is handed off only when the chosen source verifies the recipient; otherwise it stays on Aura Historia and the plugin's flow expires.

Receiving the merchant callback is required in addition to the destination rule: a permitted destination never lets the initiator collect a result by polling, because only the redirect carries the `completion_code`.

### State machine and lifetimes

`created → approved → exchanging → ready → consumed`; `created → denied | failed`; `exchanging → failed`; a handed-off `denied | failed → consumed`. Each transition is a single synchronous read-check-write in the transaction's Durable Object, so approvals, exchange claims and releases are atomic. Wrong codes, proofs, sessions, malformed input and early completion never change the record.

- The transaction expires 900 seconds after initiation (`expires_at`); consent, callback and completion must all finish by then, and no read, poll or replay extends it.
- A completion code is valid for 120 seconds after it is issued, never beyond `expires_at`.
- The broker evaluates every lifetime on its own clock. The plugin keeps its local flow state at least until `expires_at` plus 300 seconds to tolerate WordPress clock skew, and never treats a transaction as alive past what the broker reports.

### Failure semantics and cleanup

- Transaction storage that cannot be reached fails closed: initiation answers `temporarily_unavailable`, consent shows `unavailable`, and nothing falls back to unsigned state or process memory.
- Every backend call times out after 10 seconds. A claimed exchange is never retried: an upstream timeout or failure is handed off as `failed`, and the merchant starts again with fresh consent.
- If the Worker invocation ends between claiming the exchange and storing its result (a dropped connection, an evicted isolate or a deployment), the record stays `exchanging`. Completion answers `transaction_pending` until the transaction expires, then `transaction_expired`. A token issued in that window never reached the broker and cannot be revoked by it; it stays visible to, and revocable by, its owner.
- If the exchange succeeds but the result cannot be stored, or the transaction expired meanwhile, the broker revokes the token at once (`POST /v1/oauth/revoke` with the client credentials).
- An issued credential not collected within the completion-code lifetime is moved out of the readable record and revoked by the object's alarm. A failed revocation retries every 60 seconds for up to an hour after expiry; after that the record is deleted and the token remains revocable by its owner in account settings.
- A released credential is scrubbed from storage immediately. Delivery over the network is not exactly-once: if a completion response is lost, the next attempt receives `transaction_consumed` and the plugin starts again. That token cannot be revoked by the broker; it stays visible to its owner.
- Every record is deleted at its expiry. Probing an unknown `transaction_id` stores nothing.
- Initiation and completion are rate-limited to 30 requests per client address and minute (`OAUTH_BROKER_WOOCOMMERCE_RATE_LIMITER`); a missing limiter refuses rather than running unlimited. Codes and secrets carry 256 bits, so guessing is not feasible, and invalid attempts never invalidate the legitimate transaction. Bodies need a declared `Content-Length` of at most 8 KiB, checked before anything is read.

### Storage and deployment

- **Storage.** `WooCommerceOAuthBrokerTransaction` is a SQLite-backed Durable Object (declared in `exports` in `wrangler.jsonc` and reached through `exports` from `cloudflare:workers`, which `enable_ctx_exports` provides), one object per `transaction_id`, exported with the TanStack Start handler from `src/worker.ts`, the Worker's `main`. It stores the immutable initiation context, the commitment, the verifier until the exchange is claimed, timestamps, the approval binding hashes and source, the completion-code hash and, only until delivery or expiry, the credential. The raw completion secret, completion code and the user's access JWT are never stored.
- **Separation.** Durable Object namespaces belong to the Worker script, so staging (`aura-historia-staging`), production (`aura-historia`) and local development (`.wrangler/state`) keep separate transactions with no further configuration. The rate limiter namespace (`1025`) is shared; its keys carry the deployment origin.
- **Deployment.** The class is declared in `exports` rather than `migrations`, and the Worker has no `durable_objects` binding to it, because `wrangler versions upload`, which production releases and Cloudflare's branch builds use, refuses pending migrations and bindings to a class not yet provisioned; declarative exports are provisioned when a version is deployed. Staging and production therefore create the store with their regular deployments; no manual step is needed. Prefer a forward fix over rolling production back to a release from before the store existed. Deploying does not revoke existing credentials.
- **Local development and tests.** `pnpm dev` runs the Durable Object and rate limiter locally. Set `VITE_APP_URL=http://localhost:3000` (to accept a local WordPress on loopback HTTP), `VITE_API_URL` and the client credentials in `.env.local`/`.dev.vars`. Unit tests alias `cloudflare:workers` to `src/test/cloudflareWorkersStub.ts` and run the Durable Object on real SQLite (`src/test/durableObjectState.ts`, `node:sqlite`), so atomicity and scrubbing are exercised against the same SQL.

### Responses, logging and privacy

Every broker response carries `Cache-Control: no-store`, `Pragma: no-cache`, `Referrer-Policy: no-referrer` and `X-Content-Type-Options: nosniff`, and none sets CORS headers. Logs contain only an operation, an HTTP status or failure kind, and a known OAuth error identifier; never codes, secrets, verifiers, tokens, states, transaction payloads, return URIs or request bodies. Analytics do not run on these endpoints.

Privacy review: the broker processes OAuth routing and permission data, the user's source grants and the merchant's site address, and briefly holds an issued token for delivery. It adds no processor or analytics destination; the transaction store is Cloudflare, already the hosting processor, and the session-binding cookie is strictly necessary for the requested connection and expires with it. Records are deleted at expiry (at most 15 minutes, plus up to an hour for a pending revocation). The partner/API and security-data sections of the privacy policy in all five locales continue to cover this processing; consent copy explains that source selection does not restrict token permissions.
