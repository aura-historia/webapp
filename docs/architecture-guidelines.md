# Architecture Guidelines

## Stack choices to preserve

- React, TypeScript strict, Vite, TanStack Router/Start, TanStack Query, Tailwind CSS v4, shadcn/Radix-style primitives.
- File-based routes in `src/routes`.
- Generated OpenAPI client and React Query helpers in `src/client`; do not hand-edit generated files.
- Internal domain mapping in `src/data/internal` to avoid leaking API DTOs into UI components.
- Reusable app libraries in `src/lib`, shared hooks in `src/hooks`, generic UI in `src/components/ui`.

## Feature slicing

Prefer feature/domain boundaries over broad flat additions.

- New cohesive product areas belong in `src/features/<feature-name>` when they have their own pages, components, hooks, API helpers, types, or workflows.
- Existing domain component areas under `src/components/<domain>` may be extended when the pattern already exists there (`account`, `search`, `product`, `shop`, `watchlist`, etc.).
- Keep route files thin: route setup, loaders/head metadata, params/search parsing, and composition. Put substantial UI/workflow logic in components/features/hooks.
- Put API-to-domain conversion in `src/data/internal/**`, not inline in rendering components.
- Place tests close to implementation in `__tests__` directories following current patterns.

Suggested feature layout, only adding folders that are needed:

```text
src/features/<feature-name>/
  api/
  components/
  hooks/
  lib/
  pages/
  types/
```

## Data fetching and SSR

- Prefer TanStack Router loaders for SSR-friendly prefetch when route-level data is needed before render or directly route-dependent.
- Use TanStack Query for cache, mutation, and client interaction patterns.
- Respect authenticated vs unauthenticated cache behavior. Do not cache personalized data as shared public data.
- Parse language via existing language utilities and currency/preferences via existing preference helpers.
- Server code runs on Cloudflare Workers (workerd), whose `fetch` and `Request` support only `redirect: "follow"` and `"manual"` and throw a `TypeError` for `"error"` before anything is sent; the generated client returns that as a failed result with no response. Use `"manual"` and treat an unexpected redirect status as a failure. Browser-only code may use `"error"`.
- Keep route `validateSearch` output URL-safe (strings, numbers, booleans, and arrays). Product search uses `validateSearchUrlParams` for route state and `validateSearchParams` to map date strings to domain `Date` values at the page boundary. Returning `Date` objects from route validation can cause repeated canonical URL redirects.

## Generated code

- `src/routeTree.gen.ts` is generated by TanStack Router tooling.
- `src/client/**` is generated by OpenAPI tooling.
- If generated types/hooks are wrong, update the source spec/generator and run `pnpm openapi-ts`; do not patch generated output manually.
- `mcp/mcp-tools.json` is synced from the backend's MCP tool snapshot by `scripts/sync_mcp_tools.py` (see `docs/api-contracts.md#mcp-tool-snapshot`).
- The client and partner API reference share the pinned contract at `openapi/swagger.yaml`. Replace that capture deliberately before adopting backend changes, then regenerate both artifacts. See `docs/api-contracts.md` for the adoption checklist, known gaps and DTO mapping rules.

## Forms

- Prefer `react-hook-form` with Zod validation for new/refactored forms unless an existing feature deliberately uses another pattern.
- Use the `react-hook-form-writer` project skill for non-trivial form work.

## Effects and state

- Derive values during render when possible.
- Use effects only for external synchronization: browser APIs, subscriptions, analytics, third-party widgets, or imperative integrations.
- Use the `react-useeffect` or `writing-react-effects` skills when touching non-trivial effects.

## Pre-rendering

Exclude any routes that are only accessible through authentication or contain highly personalized content from pre-rendering and indexing.

- Pre-rendering is enabled by default, only apply it to routes where it makes sense
- Use `noIndex: true` in route metadata
- Edit `src/lib/seo/staticPages.ts` to add or remove prerendered pages; `vite.config.ts` reads it

## Indexing (`robots.txt`, sitemap)

- Keep a page out of search results with a `noindex` robots tag, never with a `Disallow` rule: a
  disallowed page cannot be fetched, so its `noindex` goes unseen and it can still be indexed from
  external links. `public/robots.txt` disallows only non-page endpoints (`/api/`).
- Legal pages (imprint, privacy, terms), login, consent settings and every authenticated area are
  `noindex`. Prerendered `noindex` pages set `indexable: false` in `src/lib/seo/staticPages.ts`, which
  leaves them out of `sitemap.xml`.
- robots.txt rules are path-prefix matches and every page carries a language prefix, so a rule that
  must match pages needs one (`/*/…`).
- Search result pages (`/search`, `/search/shops`) are `noindex, follow` (`followLinks: true`): their
  filter combinations are endless, but crawlers should follow their links to listings and sources.
- `src/lib/seo/__tests__/robotsTxt.test.ts` keeps robots.txt, the sitemap and route `noindex`
  settings consistent.

### Canonical URLs and trailing slashes

Every page URL has a language prefix and no trailing slash: `/de`, `/de/about-us`,
`/de/products/…`. Canonical, hreflang, `og:url`, sitemap and `llms.txt` URLs use that form, so each
one answers `200` without a redirect.

- Prerendered pages are written as `/de/about-us/index.html`. `assets.html_handling` in
  `wrangler.jsonc` is `drop-trailing-slash`, which serves them at `/de/about-us` and redirects
  `/de/about-us/` there. Do not switch it back to the default (`auto-trailing-slash`), which
  redirects the other way and turns every canonical URL into a redirect.
- `localizedStaticPagePath` in `src/lib/seo/staticPages.ts` names prerendered pages, the language
  root without a slash.
- The domain root `/` redirects each visitor to their language (302); `x-default` hreflang points to
  the English page.

### Sitemaps

robots.txt names two sitemaps:

- `/sitemap.xml`, written at build time from `src/lib/seo/staticPages.ts` (indexable pages only).
- `/sitemaps/products.xml`, built by the Worker (`src/features/product/catalog/server/productSitemap.ts`)
  from the public product search: the 1,000 most recently updated listings, each in every
  language, with its first image cleared for display. The edge keeps it for six hours. The cost is
  fixed (ten anonymous search requests per build), whatever the catalogue size. Listings whose
  content needs consent stay out. Listing every product needs a backend sitemap feed; until then
  older listings are found through links (similar items, source pages).
- Source profiles stay out of sitemaps
  (see `docs/landing-page-prerendering-guidelines.md#public-listing-source-discovery`).

### Structured data (JSON-LD)

Structured data repeats what the page shows; nothing is only machine-readable. Serialize it with
`jsonLdScript` / `serializeJsonLd` from `src/lib/seo/jsonLd.ts`: the router writes script children as
raw HTML, and the helper escapes `<` so listing or source text cannot close the script element.

- Home: Organization and WebSite (which names the site in Google results), the page, and the
  visible FAQ (`src/features/landing/lib/landingStructuredData.ts`). The Organization node lives in
  `src/features/app-shell/lib/siteStructuredData.ts`; the about page reuses it.
- Listing pages (`src/features/product/detail/lib/seo/productJsonLd.ts`): a Product with an Offer
  only for an active listing with a current asking price above zero. The Offer names the source as
  `seller` (linked to its profile page) and points to the listing page. `sku` is the source's own
  listing ID when it has 1–50 characters (Google's limit); `productID` is ours. Without an offer
  (price on request, sale observations, withdrawn) the page is an ItemPage, because Google counts
  a Product without offers, reviews or ratings as an invalid item.
- The listing data has no brand, GTIN, condition, ratings, reviews or return policy, so none are
  published; Search Console reports them as optional. Shipping details will come with the
  shipping data.
- Source profiles: a CollectionPage about the source, from its allowlisted public fields.
- About and the Barnebys comparison: see their builders in `src/features/about` and
  `src/features/comparison`.

### Content Signals

`public/robots.txt` tells every crawler how it may use the site's content, as
[Content Signals](https://contentsignals.org) in the `User-agent: *` group:
`search=yes, ai-input=yes, ai-train=no`. Search engines and AI answers may use the site; AI
training may not, because listing texts and images belong to dealers and auction houses. The file
carries the standard Content Signals policy text, which makes `no` an express reservation of rights
under Article 4 of the EU copyright directive (2019/790).

- Every HTML page repeats the value in a `Content-Signal` response header: Worker-rendered pages get
  it in `src/server.ts`, prerendered pages from `public/_headers`. Cloudflare's Markdown for Agents
  keeps that header on the Markdown it converts a page to; without it, Cloudflare adds a default
  that allows AI training.
- `CONTENT_SIGNAL` in `src/lib/seo/contentSignals.ts` is the value; tests keep robots.txt and
  `public/_headers` equal to it. Change them together, and only as a product and legal decision.
- robots.txt states preferences; Cloudflare enforces them. AI Crawl Control blocks AI training
  crawlers at the edge and must allow search and user-driven agent crawlers, such as `ChatGPT-User`,
  `Claude-User` and `Claude-SearchBot`.
- Keep Cloudflare's managed robots.txt (Bot Preference Sync) off. It prepends its own content signals
  and `Disallow` groups, so this file would stop being the only source.

## Agent discovery

### `llms.txt`

`public/llms.txt` follows the [llms.txt specification](https://llmstxt.org): one H1, a blockquote
summary, unheaded guidance, then H2 sections that contain only `- [name](url): notes` link lists,
with secondary links in a final `## Optional` section. It is served as a static asset with UTF-8
plain-text headers from `public/_headers`, announced by a `rel="describedby"` link in the root route
head and by a comment in `public/robots.txt`.

- Update it when public routes, the public URL patterns it describes, the REST API or MCP endpoints,
  API documentation URLs or partner integration listings change. An MCP host change also needs the
  DNS-AID record in the Cloudflare zone updated (`docs/dns-aid.md`).
- Use absolute HTTPS URLs that avoid redirects where possible; page URLs have no trailing slash
  (see [Canonical URLs](#canonical-urls-and-trailing-slashes)). Prefer Markdown sources (such as `https://docs.api.aura-historia.com/*.md`) over HTML.
- List only public content; never link account, partner, admin or OAuth pages, and keep claims as
  restrained as product copy.
- `src/lib/seo/__tests__/llmsTxt.test.ts` checks the structure and shared links.

### Discovery documents

The backend writes every agent discovery document; the webapp only decides which website paths
publish them. Never write or edit discovery content here. The backend's
[agent discovery contract](https://github.com/aura-historia/backend/blob/develop/docs/agent-discovery.md)
owns the bodies, media types and the environment's URLs.

| Website path | Backend source |
|---|---|
| `/.well-known/mcp/server-card.json` | MCP host, same path |
| `/.well-known/api-catalog` | API host, same path |
| `/.well-known/oauth-authorization-server` | API host, same path; never cached here |
| `/.well-known/ai-catalog.json` and `/.well-known/ard.json` | API `/v1/site-discovery/ai-catalog.json` |
| `/.well-known/poppy.json` | API `/v1/site-discovery/poppy.json` |
| `/.well-known/agent-skills/index.json` and `/.well-known/agent-skills/{name}/SKILL.md` | API `/v1/site-discovery/agent-skills/…` |
| `/auth.md` | API `/v1/site-discovery/auth.md` |

- The table lives in `src/features/agent-discovery/server/agentDiscoveryRoutes.ts`. `src/server.ts`
  answers these paths before TanStack Start, so the root route never locale-redirects them or
  renders HTML. Other paths below `/.well-known/agent-skills/` are a JSON `404` without a backend
  call; skill names must match the Agent Skills name rules.
- `src/worker.ts`, the Wrangler `main`, must re-export `src/server.ts`. Re-exporting
  `@tanstack/react-start/server-entry` there instead serves TanStack Start's default entry and
  silently skips the forwarding table and the site-wide headers (`src/__tests__/server.test.ts`).
- Deliberately not published: `/.well-known/openid-configuration` (Aura is no OpenID provider for
  agents), `/.well-known/oauth-protected-resource*` (website pages are no protected resources) and
  `/.well-known/acp.json`.
- Forwarding (`agentDiscoveryForwarding.ts`) accepts `GET` and `HEAD` only and sends the backend a
  fresh `GET` without the query or any client header, so cookies and `Authorization` never leave.
  It passes the status, `Content-Type` with its parameters, `Access-Control-Allow-Origin` and, on the
  API catalog, `Link` through unchanged, and the body byte for byte: the skills index pins each
  `SKILL.md` by its `sha256` digest, so never decode, re-encode or reformat a body.
- A backend that is unreachable, times out, redirects or answers `5xx` gets a JSON `502` (`503` when
  the backend answered `503`), never the app's HTML. Backend `4xx` pass through, uncached.
- A `200` is kept in the Workers Cache API for `AGENT_DISCOVERY_EDGE_CACHE_TTL_SECONDS` (300 s, the
  backend's shared TTL), keyed by website path. Every cached document uses the same TTL, so the
  skills index and each `SKILL.md` agree on digests again shortly after a backend release. Clients get
  `public, max-age=0`. The OAuth metadata is never cached here; its `no-store` passes through.
- The API origin is `VITE_API_URL`; the MCP origin is `VITE_MCP_URL` or, by default, the API host's
  `mcp.` sibling (`getMcpBaseUrl` in `src/lib/apiBaseUrl.ts`), so staging and Wrangler Previews built
  against the stage API use the stage MCP host.
- Every HTML page names the API catalog in a `Link: </.well-known/api-catalog>; rel="api-catalog"`
  header (RFC 9727 §3): `src/server.ts` adds it to rendered pages and `public/_headers` to
  prerendered pages, one rule per language. The root route head links the AI catalog with
  `rel="ai-catalog"`, and `public/llms.txt` links the server card, API catalog, skills index and
  `auth.md`. Add a language's `_headers` rule with the language.
- A new website document needs a row here, a table entry and tests in
  `src/features/agent-discovery/`, and the backend's route. The optional DNS records that point to the
  AI catalog are in `docs/dns-aid.md`.

### WebMCP

Browser agents with [WebMCP](https://webmachinelearning.github.io/webmcp/) get the site's tools on
every page. It is the only discovery piece that runs in the browser. The backend's MCP server owns
the catalogue tools, and the webapp copies none of their definitions by hand. The code lives in
`src/features/agent-discovery/webmcp/`.

- **Registration:** `startWebMcp` looks for `document.modelContext`, then `navigator.modelContext`
  (older Chrome builds). Without either, and on the server, it does nothing. Otherwise it
  lazy-loads `registerWebMcpTools.ts` and registers the tools once per document; aborting its
  `AbortSignal` unregisters them. `getRouter` (`src/router.tsx`) calls it when the client creates
  the router, before hydration. Agents and scanners look for tools on page load, and hydration
  finishes after the `load` event, so a root-layout effect would register them too late. Never
  register tools per route. Nothing is rendered, so server markup does not change.
- **Catalogue tools:** registered from the synced snapshot `mcp/mcp-tools.json` (see
  [API contracts](api-contracts.md#mcp-tool-snapshot)). Every tool whose
  `_meta["aura.historia/access"]` is `public` keeps the server's `name`, `description`,
  `inputSchema` and `readOnlyHint`, and gets `untrustedContentHint: true`, because listing text comes
  from third-party providers and can carry prompt injection. Signed-in tools come later
  ([#1245](https://github.com/aura-historia/webapp/issues/1245)): the MCP server rejects the
  website's Cognito JWTs. Never call `tools/list` at runtime. It is a POST the CDN cannot cache, so
  every page view in a WebMCP browser would invoke the MCP Lambda and use up its small reserved
  concurrency.
- **Calls:** a request goes out only when an agent executes a tool. `callMcpTool` sends one
  anonymous JSON-RPC `tools/call` to `{MCP origin}/v1` under revision `2026-07-28`:
  - There is no `initialize` step. `params._meta` carries the protocol version, client info and
    capabilities.
  - The `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` headers must match the body; a mismatch
    returns `-32020`.
  - Requests send no cookies or credentials. The agent's cancellation signal aborts the request.

  A call resolves with the result's `structuredContent` and rejects with one of these errors:
  - `McpToolError`: an `isError` result, with the tool's error code such as `NOT_FOUND`.
  - `McpInvalidParamsError`: `-32602`, an unknown tool or invalid arguments, usually a backend
    change this repo has not synced yet.
  - `McpProtocolError`: any other JSON-RPC error.
  - `McpTransportError`: no valid JSON-RPC response arrived (a network, CORS or HTTP failure, or
    a malformed answer). The request accepts JSON and event streams, as Streamable HTTP requires,
    but the server answers tool calls with JSON only.
- **Origins:** the MCP server checks `Origin` itself, in addition to gateway CORS. Production admits
  `https://aura-historia.com`; stage admits `https://stage.aura-historia.com` and
  `http://localhost:3000`. On any other page origin, such as a Wrangler Preview, only the navigation
  tools are registered (`mcpPageOrigins.ts`; keep it in line with the backend's front-door origins).
  A self-hosted MCP server set through `VITE_MCP_URL` is expected to admit the page itself.
- **Navigation tools:** the webapp's own tools are UI actions:
  - `openProductListingPage` (`productListingTitleSlugId`)
  - `openProductListingSearch` (`query`)
  - `openListingSourcePage` (`listingSourceSlugId`)

  They navigate with the router and keep the current language. A full page load would destroy the
  document and the pending call. They resolve with the opened page's absolute URL. They reject when
  the page is not found or fails to load, when a later navigation replaced it, or when the agent
  cancels. The search tool needs a query of at least `MIN_SEARCH_QUERY_LENGTH` characters, like the
  search page, and is left out while `VITE_FEATURE_SEARCH_ENABLED` is off. `registerTool` rejects
  duplicate names, so their names start with `open`, a prefix the snapshot sync refuses for backend
  tools.
- Tool descriptions address agents and are written in English, like the backend's, so they are not
  translated. The tools have no `title`.
- To verify a deployment, scan [isitagentready.com](https://isitagentready.com/aura-historia.com)
  and check that `checks.discovery.webMcp` passes.

## Validation

Start with the narrowest relevant checks, then broaden when useful:

- Unit/component tests close to changed code: `pnpm test -- <pattern>` when supported by Vitest.
- Lint/check changed code: `pnpm lint` or `pnpm check` when appropriate.
- Build after routing/SSR/i18n changes: `pnpm build`.
- Ignore E2E tests for now unless the user explicitly asks for them.
